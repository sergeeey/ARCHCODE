## Пролог: два слоя правды

С первых же канонических документов проект описывает себя не как «ещё один скоринг вариантов», а как рамку для честной проверки утверждений. В [README.md](../README.md) публичный слой прямо фиксирует итог фальсификации (AUC как артефакт категории, within-category около случайного уровня, провал кросс-локусного переноса) и формулирует, что **выжило** (движок, validation suite, узкие острова сигнала вроде TP53 splice_region). Параллельно [PROJECT_CANON.md](../PROJECT_CANON.md) вводит трёхслойную модель: **Public Canonical**, **Technical Full-Scope**, **Legacy** — то есть архитектурное решение на уровне *управления смыслом репозитория*, а не только кода.

**Интерпретация:** первоначальная гипотеза «физика петель + контактные карты дадут дополнительную дискриминацию к простым признакам» по текущему публичному канону **не подтверждена** как универсальный предиктор; зато гипотеза второго порядка — «нужна воспроизводимая инфраструктура, которая *ломает* слабые claims» — воплощена явно (validation suite, контракты, сканеры канона).

## Глава 1. Зарождение: скелет, визуализация, обещание физики

**Наблюдение (git):** цепочка ранних коммитов (`9220907` Initial commit → `d55e819` public skeleton v0.1 → `b1b34bb` ARCHCODE v1.0 с «neon tube visualization») показывает траекторию от заготовки к «публикационно оформленному» релизу с UI. Упоминание в истории переноса CLI «from TERAG» (`eb24427`) намекает на **повторное использование инженерных шаблонов**, а не чистый greenfield.

**Наблюдение (код):** ядро симуляции живёт в TypeScript: например [MultiCohesinEngine.ts](../src/engines/MultiCohesinEngine.ts) — классический цикл экструзии с конфигурируемой выгрузкой, опционально Kramer kinetics, spatial loader, телеметрия барьеров. Это говорит о замысле **интерактивного, воспроизводимого** физического движка в браузерном стеке (React, Three.js — см. [package.json](../package.json)).

**Наблюдение (контраст):** публичный Python CLI [cli.py](../src/archcode/cli.py) — скелет с сообщениями вроде «Core loop-extrusion engine is private»: фактически «полный» движок в репозитории на TS, а Python-пакет выполняет роль **оболочки/заглушки** или будущего моста. Это важный архитектурный факт: **двуязычие не симметрично** — источник истины для экструзии в TS.

**Интерпретация:** ранний замысел, судя по структуре, ближе к «демонстрабельному исследовательскому инструменту + симулятор», чем к узкому CLI-библиотечному пакету.

## Глава 2. Биофизика в коде: честность происхождения параметров

Сильная сторона проработки — явная маркировка происхождения констант. В [biophysics.ts](../src/domain/constants/biophysics.ts) комментарии разделяют литературные ориентиры (Davidson 2019 по скорости экструзии, Gerlich/Hansen по residence) и **MODEL PARAMETER** (например, `PROCESSIVITY_KB: 600` с явным контрастом к ~33 kb из одномолекулярных данных). Блок `COHESIN_KINETICS` помечает `alpha`/`gamma` как **EXPLORATORY PARAMETERS** и прямо запрещает выдавать их за «fit к FRAP в репозитории».

**Совпадение замысла и реализации:** после аудита целостности (см. [CLAUDE.md](../CLAUDE.md), [docs/VALIDATION.md](VALIDATION.md)) код констант **подстроен под дисциплину доказуемости**: меньше скрытых «подогнанных» чисел, больше подписей.

**Натяжка / неоднозначность:** в [gold-standard.test.ts](../src/__tests__/regression/gold-standard.test.ts) встречается формулировка про «grid search optimization» для параметров по умолчанию — без чтения всего файла нельзя утверждать, что это claim о публикационном фите; это **место, где читателю кода полезно свериться с комментариями и VALIDATION**, чтобы не смешать инженерный тюнинг с биологической калибровкой.

## Глава 3. Валидация и фальсификация как «вторая система»

Появление [validation_suite/](../validation_suite/) и [validation_suite/README.md](../validation_suite/README.md) — переломный архитектурный паттерн: рядом с моделью строится **баттерея тестов, направленных на опровержение** (CTCF shuffle, простые baseline, within-category, ablation, cross-locus, robustness). Это не «дополнительные unit-тесты», а **отдельный контур смысла**: методология Popper-style встроена в репозиторий.

**Наблюдение (инженерия):** пути к конфигам и результатам задаются относительно корня репозитория в [repo_paths.py](../validation_suite/repo_paths.py); при необходимости корень можно переопределить переменной окружения `ARCHCODE_ROOT`.

**Связь с git:** поздние коммиты (`feat: VUS decision router + matched-control kill test`, `feat: establish three-layer canon`, серия `fix(integrity)`) показывают фазу, когда проект **перестраивает публичный нарратив под результаты собственных же тестов** — редкий и честный сценарий в научно-инженерных репозиториях.

## Глава 4. Канон и автоматический контроль дрейфа смысла

[validate_project_canon.py](../scripts/validate_project_canon.py) — не просто линтер: он знает **запрещённые формулировки** для публичного слоя (`variant pathogenicity prediction`, устаревшие счётчики вариантов/pearl и т.д.) и проверяет наличие legacy-путей. Это архитектурное решение уровня **Governance-as-Code**: снижает риск регрессии маркетинговых формулировок в документах после правок.

**Интерпретация:** эволюция проекта включает осознанный **институциональный слой** (канон, скрипты, CLAUDE/AGENTS контракты) — не только алгоритмы.

## Глава 5. Что действительно «работает хорошо» (наблюдаемая ценность)

1. **Движок экструзии на TS** — связный домен (модели, константы, движки, тесты Vitest), пригодный как открытый быстрый симулятор контактных эффектов для гипотез (без автоматического приравнивания к клинике).
2. **Validation suite как методологический артефакт** — чёткие kill-criteria и интерпретационная таблица; это может жить **независимо** от ARCHCODE как шаблон для других 3D-моделей.
3. **Дисциплина целостности** — многоуровневая документация, бан паттернов, разделение public/technical/legacy снижает класс ошибок «красивое README не совпало с данными».
4. **Регрессионные тесты «золотых локусов»** — институционализируют ожидания по поведению на HBB/SOX2/Pcdh и т.д. ([gold-standard.test.ts](../src/__tests__/regression/gold-standard.test.ts)).

## Глава 6. Где замысел расходится с текущей идентичностью (честные несоответствия)

- **package.json** — ключевые слова и описание выровнены с каноном (см. текущий [package.json](../package.json)): убрано позиционирование вокруг «pathogenicity prediction» в keywords.
- **Двуязычие TS/Python** без симметричного API: для внешнего пользователя «где главный вход» менее тривиально, чем хотелось бы.
- **Entrypoint validation suite:** в README фигурирует `python -m validation_suite`; для полной согласованности может потребоваться `__main__.py` — **UNVERIFIED** без отдельного прогона в вашей среде.

## Глава 7. Перспективы архитектуры

**Наблюдение → потенциал:** разделение (1) быстрого симулятора, (2) пайплайна данных ClinVar/атласов, (3) фальсификационного контура — уже есть. Логичное развитие без смены сути: CI-матрица для suite; оформить TS-движок как явный primary package (версия v2.17 в README vs 2.0.0 в package.json уже отражено в [PROJECT_CANON.md](../PROJECT_CANON.md) как *намеренный* split).

**Интерпретация:** масштабируемость здесь скорее **методологическая** (перенос suite на другие модели, другие атласы), чем «больше локусов = сильнее предиктор» — что согласуется с текущими выводами README.

## Эпилог: итоговая оценка

**Сильные стороны (по фактам репозитория):** зрелый симуляторный стек на TypeScript; богатая экосистема скриптов; выдающаяся для академического OSS **инфраструктура фальсификации и канонического контроля**; последовательная коррекция публичных claims после аудита (видно по истории git и структуре docs).

**Критические моменты:** риск путаницы ролей Python/TS; необходимость явной документации entrypoint’ов; отдельные формулировки в тестах/комментариях требуют внимания, чтобы не восстанавливали отозванные narrative.

**Возможности улучшения (без фантазий):** единый «entrypoint matrix» в README (что запускать для воспроизведения какого артефакта), явная схема версий (уже частично задокументирована).
